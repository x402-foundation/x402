SVM exact payments support transaction version 1 (SIMD-0385). Facilitators advertise and accept `extra.transactionVersions` `[0, 1]`, and clients build the highest version they share with the facilitator; pass `transaction_versions=[0]` to `ExactSvmScheme` / `ExactSvmSchemeV1` to keep a signer that cannot sign version 1 on version 0. A client-built version 1 transaction carries no ComputeBudget instructions: its message config sets the compute unit limit, a 4 MiB loaded-account-data limit (`DEFAULT_LOADED_ACCOUNTS_DATA_SIZE_LIMIT`) and the total priority fee in lamports, and it may be up to 4096 bytes. The facilitator verifies the version 1 layout (TransferChecked first, then up to four Lighthouse/Memo instructions), requires the compute unit and loaded-account-data limits, caps the priority fee as `priorityFee * 1000000 <= maxPriceMicroLamports * computeUnitLimit`, and rejects a requested heap size or any ComputeBudget instruction with the new `invalid_exact_svm_payload_transaction_loaded_accounts_data_size_limit_missing`, `invalid_exact_svm_payload_transaction_v1_heap_size` and `invalid_exact_svm_payload_transaction_v1_compute_budget_instruction` reasons. Verifiers also enforce the serialized size limit of the message version (1232 bytes for legacy and version 0, 4096 bytes for version 1) and reject an oversized payment with the new `invalid_exact_svm_payload_transaction_size_exceeded` reason.
