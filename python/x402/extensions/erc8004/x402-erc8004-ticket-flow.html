x402 × ERC-8004 — ticket flow (v2)

1-step x402 (same URL). Spec: specs/extensions/erc8004_ticket_v2.md

What we added: two small contracts

Contract 1 · the ticket

X402AgentReputation

A paid x402 call mints a consume-once ticket — proof "this client paid this agent."

  • Settles exactly like x402 — EIP-3009 (USDC) or Permit2 via the canonical proxy (DAI) — then mints in the same tx.
  • Permissionless: anyone can relay a signed payment; no facilitator allowlist.
  • Stores plain payment data only: payer, agentId, agentAddress, token, amount, consumed.
  • Calls: settleAndMintTicket…() → ticketId; consumeTicket(ticketId) → agentId.
Contract 2 · the feedback bridge

FeedbackGateway (EIP-7702)

Turns a ticket into client-authored feedback on the canonical ERC-8004 registry.

  • The client delegates its EOA to this contract (EIP-7702). Its code then runs as the client — so msg.sender stays the client.
  • In one call: consumeTicket (gate) → ReputationRegistry.giveFeedback (author = client).
  • Self-paid submitFeedback · sponsored submitFeedbackFor (client-signed intent, relayer pays gas).
  • Stateless chain-singleton — deploy once per chain, holds no funds.
Why two contracts? The canonical ReputationRegistry credits feedback to msg.sender, so the client must be the caller. EIP-7702 makes that possible — but delegating your EOA to a contract is risky, so the delegate (FeedbackGateway) is kept tiny and fund-free, separate from the payment/ticket logic.
pay (HTTP 402) ─▶ X402AgentReputation: settle + mint ticket │ delegate EOA (7702) ─▶ FeedbackGateway ──▶ consumeTicket ──▶ canonical ReputationRegistry.giveFeedback (runs as the client — feedback authored by the payer)

Summary

  • Contracts: X402AgentReputation — x402 settle + consume-once ticket. FeedbackGateway (EIP-7702 delegate) consumes the ticket and forwards giveFeedback to the canonical ReputationRegistry — feedback is stored there, authored by the client.
  • No bind at mint: client signs payment only; settlement is permissionless (gated by the signed authorization), so no facilitator allowlist.
  • Attestation: agent signs EIP-712 after handler → X-X402-Interaction-Attestation (best-effort; missing → CLIENT_ONLY).

Feedback paths

Path A — Self-paid (EIP-7702): payer delegates its EOA to FeedbackGateway and calls submitFeedback on itself → consumeTicket + canonical giveFeedback (msg.sender = client).
Path B — Sponsored (EIP-7702): payer signs a set-code authorization + EIP-712 FeedbackIntent; a relayer submits submitFeedbackFor and pays gas. Feedback is still authored by the client.

Phases (one paid request)

0 — Discover

GET → 402 with extensions.erc8004.agentId. Client echoes agentId into payment payload (no bind hashes).

1 — Sign payment

Standard x402 token authorization (EIP-3009 / Permit2 / ERC-20).

2 — Paid retry

GET + X-PAYMENT → verify → settle.

3 — Settle + mint (one tx)

settleAndMintTicket*(payer, agentId, agentAddress, payment) — plain ticket fields stored. ticketId on PAYMENT-RESPONSE.

4 — Serve + attest (best-effort)

Handler runs. Server signs InteractionAttestation from raw request/response bytes. If signing fails: still return 200 without header.

5 — HTTP response

200 + body + PAYMENT-RESPONSE + optional X-X402-Interaction-Attestation.

6 — Feedback (later, EIP-7702)

Client builds the artifact (embeds attestation when present), delegates its EOA to FeedbackGateway → consumeTicket (ticket consumed=true) + canonical ReputationRegistry.giveFeedback, authored by the client.

7 — Off-chain verify

verify_feedback: ticket match → attestation field compare → FULL / CLIENT_ONLY / DISPUTED / REJECTED.
