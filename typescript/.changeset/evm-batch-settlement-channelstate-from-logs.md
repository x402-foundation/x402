The batch-settlement facilitator now derives the deposit and refund settle `extra.channelState` from the confirmed receipt's `Deposited`, `Claimed` and `Refunded` events plus the pre-transaction state, instead of polling channel state after confirmation. A deposit receipt without a `Deposited` event for the channel fails with `invalid_batch_settlement_evm_deposit_transaction_failed`, and a receipt whose `logs` field is missing fails with the new `invalid_batch_settlement_evm_receipt_logs_unavailable`; both are terminal. The refund `withdrawRequestedAt` now survives a partial withdrawal reduction and `totalClaimed` comes from the bundled `Claimed` event. Voucher verify re-reads channel state for up to `CHANNEL_STATE_POLL_MS` while the balance cannot cover `maxClaimableAmount`, and the server deposit after-settle hook never lowers a stored `totalClaimed`. `BatchSettlementEvmScheme` (facilitator) now takes a `BatchSettlementFacilitatorEvmSigner`, whose `waitForTransactionReceipt` returns required `logs`; this is type-only, signers built with `toFacilitatorEvmSigner` over a viem client already conform, and a custom signer that declares `logs` optional must make it required. The `channelState` wire shape is unchanged.
