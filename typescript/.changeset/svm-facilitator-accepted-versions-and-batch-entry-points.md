SVM facilitators take their accepted transaction-version set, apply the spec's sponsor defaults, and close several `upto` and `batch-settlement` verify gaps; the batch scheme gains single-shot entry points.

- The `exact`, `upto` and `batch-settlement` facilitators take a `transactionVersions` option (default `[0, 1]`), advertise it as `extra.transactionVersions`, and reject a client transaction of any other version with `unsupported_transaction_version` before inspecting its instructions. A legacy message is accepted exactly when version 0 is. An empty list or an entry other than `0`/`1` throws at construction. `isAcceptedTransactionVersion` takes the accepted set as an optional second argument; `normalizeAcceptedTransactionVersions` validates it.
- **Behaviour change:** the `exact` facilitator now defaults `maxRequiredSignatures` to 2 (scheme_exact_svm.md §2.1.4: no required signer beyond the client and the sponsor) and `maxComputeUnits` to 400,000 (the §2.2.1 reference default, applied to a version-0 `SetComputeUnitLimit` and a version-1 header `computeUnitLimit` alike). Operators whose wallets need more set them explicitly. While `maxComputeUnits` is unset, a smart-wallet transaction above 400,000 CU still reaches Path 2 and is judged against `smartWalletMaxComputeUnits` (a transaction invoking no allowlisted wallet program keeps `compute_limit_instruction_too_high`); an explicit `maxComputeUnits` is a hard ceiling for both paths. `maxRequiredSignatures` is checked before path dispatch, so it bounds smart-wallet transactions too: a threshold multisig whose members co-sign the payment transaction is refused with `excessive_signers` until it is raised to the client signers plus the sponsor.
- `upto`: the read-only `verify` refuses an open whose channel already exists (`invalid_upto_svm_channel_already_open`), as the deposit settle does; `isUptoSvmPayload` accepts `openSlot` as the JSON number the scheme types it as as well as the decimal string; `verifyOpenTransaction` refuses bytes after the open args.
- `batch-settlement` facilitator: verify checks each settlement ATA (payer return, receiver, treasury) is an initialized, unfrozen token account of the declared program for the mint and owner with no extension beyond ImmutableOwner, checks the payer's ATA holds the deposit or top-up, and, without `extra.recentSlot`, judges `channelConfig.openSlot` against the cluster slot. Failures are `invalid_batch_settlement_svm_settlement_simulation` and `invalid_batch_settlement_svm_setup_transaction`. A version-1 `request_close` to a version-0-only facilitator keeps `unsupported_transaction_version`.
- `batch-settlement` client refuses a challenge whose `extra.feePayer` is its own key (`invalid_batch_settlement_svm_fee_payer_mismatch`), and rejects a corrective `voucherState` with a nonzero `expiresAt`.
- `batch-settlement` resource server refuses a voucher or authorization on a channel it holds as closing with `invalid_batch_settlement_svm_channel_closing`, and a client-mode refund whose voucher is not the accepted cumulative with `invalid_batch_settlement_svm_close_state` (was `cumulative_amount_mismatch`).
- New exports: `findPaymentChannelPda`, `getChannelDistributionHash`, `encodeVoucherMessageBytes`; `encodeBatchVoucherMessage`, `deriveBatchChannelId`, `encodeReceiverBindingMemo`, `parseReceiverBindingMemo`; the wire guards `isBatchRequirements`, `isBatchExtra`, `isBatchPaymentPayloadEnvelope`, `isBatchSettlementResponse`, `isBatchPaymentRequired`, `isBatchChannelState`, `isBatchVoucherState`, `isTransactionVersionList`; `checkCorrectiveState`, the single-shot check a client runs before adopting a corrective 402; and `buildBatchVoucherPayload`, `buildBatchTopUpPayload`, `buildBatchRefundPayload`, which build one operation for a channel the caller tracks without the client's channel storage. `BatchExtra` gains `transactionVersions`, `maxClaimChannels` and `maxSettleChannels`.
