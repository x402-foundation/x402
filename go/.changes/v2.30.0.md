## v2.30.0 - 2026-11-04
### Added
- 'SVM exact, upto and batch-settlement: client-built transactions now support Solana transaction v1 (SIMD-0385). Facilitators advertise transactionVersions [0, 1]; clients build the highest mutually supported version, carrying the compute budget in the v1 message config (computeUnitLimit, a 4 MiB loadedAccountsDataSizeLimit, and the equivalent total priorityFee) instead of ComputeBudget instructions. svm.ClientConfig.TransactionVersions and BatchSvmClientConfig.TransactionVersions narrow the client set (e.g. []int{0} for a signer that cannot sign v1). Verifiers accept v1 exact payments (TransferChecked first, 1-5 instructions), opens, top-ups and request_close transactions, require computeUnitLimit and loadedAccountsDataSizeLimit, cap priorityFee * 1e6 <= cap * computeUnitLimit without overflow, and reject v1 messages that contain a ComputeBudget instruction or request a heap size. A message version outside legacy/0/1 is rejected from its raw bytes with unsupported_transaction_version before decoding.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'SVM batch-settlement: facilitator-built redemptions (claim, settle, seal, refund, rent cleanup) are built as Solana transaction v1 by default, with a compute unit limit sized for the batch (25,000 + 25,000 per channel, capped at 1,400,000) and a 4 MiB loaded-account-data budget. The facilitator advertises its per-transaction capacity as extra.maxClaimChannels and extra.maxSettleChannels (18 and 13 for v1, 4 for v0), rejects a larger claim or settle request with invalid_batch_settlement_svm_payload_type, and fails a redemption that does not fit rather than truncating it. Config.FacilitatorTransactionVersion and RentCleanupConfig.FacilitatorTransactionVersion choose the message version (0 or 1) of the transactions the facilitator builds itself; unset keeps v1, and 0 builds version 0 with a capacity of 4. Client-built versions are unaffected. The server copies the capacity into PaymentRequirements.extra and sizes claim and settle batches by it (4 when absent), lowered by MaxChannelsPerBatch when set.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'SVM upto and batch-settlement: Config.PaymentChannelsTreasuryOwner overrides the treasury owner the payment-channels program was built with, so distribute, the readiness simulation and rent cleanup work against a custom or local program build. The zero key keeps the deployed program''s owner for the network; paymentchannels.ResolveTreasuryOwner applies the same rule.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'EVM batch-settlement client: BatchSettlementEvmSchemeOptions.RPCURL and RPCByChainID let the EIP-2612 and ERC-20 approval gas-sponsoring extensions read token contracts and fill approval transaction fields over RPC when the signer cannot, matching the exact and upto clients.' ([#4088](https://github.com/x402-foundation/x402/pull/4088)) - Thanks [@wnjoon](https://github.com/wnjoon)!
### Changed

([#3916](https://github.com/x402-foundation/x402/pull/3916)) - Thanks [@wnjoon](https://github.com/wnjoon) and [@claude](https://github.com/claude)!

([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'SVM facilitators take their accepted transaction-version set and apply the spec sponsor defaults. The exact, upto and batch-settlement facilitator configs gain TransactionVersions (default [0, 1]), advertised as extra.transactionVersions; a client transaction of another version is rejected with unsupported_transaction_version before any instruction is inspected, and legacy is accepted exactly when version 0 is (svm.IsAcceptedTransactionVersionIn, svm.NormalizeAcceptedTransactionVersions). Behaviour change: the exact facilitator now defaults MaxRequiredSignatures to 2 (no required signer beyond the client and the sponsor) and MaxComputeUnits to 400,000 (the reference default, for SetComputeUnitLimit and the version-1 header alike). While MaxComputeUnits is nil, a smart-wallet transaction above 400,000 CU still reaches the smart-wallet path and is judged against SmartWalletMaxComputeUnits (one invoking no allowlisted wallet program keeps compute_limit_instruction_too_high); a set MaxComputeUnits bounds both paths. MaxRequiredSignatures is checked before path dispatch, so a threshold multisig whose members co-sign the payment transaction needs it raised. The upto Verify refuses an open whose channel already exists, and upto payloads accept openSlot as a JSON number. The batch-settlement facilitator checks every settlement ATA''s token state (initialized, unfrozen, mint, owner, extensions) and the payer''s balance against the deposit, and judges openSlot against the cluster slot when extra.recentSlot is absent; the client refuses extra.feePayer equal to its own key; the server refuses a voucher or authorization on a closing channel with channel_closing and an off-watermark client refund with close_state.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
### Fixed
- 'SVM verifiers enforce the serialized size limit of the message version on every client transaction they co-sign (1232 bytes for legacy and version 0, 4096 bytes for version 1). Exact rejects an oversized payment with the new invalid_exact_solana_payload_transaction_size_exceeded reason; the open, top_up and request_close verifiers reject one before checking its layout.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'SVM batch-settlement facilitator reports the spec error codes for setup transactions and the request envelope. A deposit whose open or top_up transaction fails the sponsor checks is invalid_batch_settlement_svm_setup_transaction instead of transaction_failed; a foreign binding Memo is receiver_authorizer_mismatch, a grace period other than extra.withdrawDelay is withdraw_delay_mismatch, and an unaccepted message version is unsupported_transaction_version. A deposit proof the escrow cannot cover is cumulative_exceeds_deposit rather than cumulative_amount_mismatch, and a refund of a sealed or distributed channel, or one whose voucher lies outside the settled-to-deposit range, is close_state. The batch server classifies its own setup-transaction failures the same way. Verify requires paymentPayload.accepted to equal paymentRequirements in every field except the per-402 recentBlockhash and recentSlot, and reports a mismatch (including a network mismatch) as invalid_payment_requirements instead of network_mismatch.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!
- 'SVM transaction v1 follow-ups. svm.ConfirmedTransactionInnerInstructions and the payment-channels history reader request MaxSupportedTransactionVersion 1 (svm.MaxSupportedTxVersion), so the smart-wallet post-settle check and the receiver-binding history reader handle v1 transactions instead of failing on them. The x402 v1 exact facilitator gains NewExactSvmSchemeV1WithConfig with Config.TransactionVersions (default [0, 1]; invalid values panic), advertised and enforced like the v2 facilitator''s. The batch-settlement channel manager clamps the advertised maxClaimChannels / maxSettleChannels to V1MaxClaimChannels / V1MaxSettleChannels.' ([#3971](https://github.com/x402-foundation/x402/pull/3971)) - Thanks [@lgalabru](https://github.com/lgalabru)!

VerifiedPaymentCanceledContext.VerifyResult carries the trusted verify response for after_verify_aborted. EVM batch-settlement facilitator-managed mode: settleOnCancel releases the facilitator admission lock for settlement_preflight_failed and for after_verify_aborted raised before the scheme afterVerify hook (pendingId recovered from VerifyResult); a refund-signer failure keeps the request context so the cancel can release the lock; afterVerify aborts with invalid_batch_settlement_evm_verification_state_unavailable when pendingId or the channel view (balance, totalClaimed, chargedCumulativeAmount, refundNonce, withdrawRequestedAt) is missing or malformed; afterSettle updates the replica only from a well-formed channelState or verify snapshot (a refund never falls back to its pre-refund snapshot) instead of writing zero defaults; request-context expiry is the server's own maxTimeoutSeconds (floored at 5 seconds) plus a 10-second grace. Self-managed batch settlement also releases its admission lock on settlement_preflight_failed, so a pre-facilitator settle failure no longer holds the lock until its TTL. Unchanged on the wire.'
